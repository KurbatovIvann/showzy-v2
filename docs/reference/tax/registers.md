## The open-part register API

Base: `https://cabinet.tax.gov.ua/ws/api/public/registers/`

It offers two modes, and the difference between them is the whole design
decision.

### Mode 1 — full register as CSV

Plain `GET`, no token shown in the documentation's own examples:

| Register | Path under `/export/` |
| --- | --- |
| Платники єдиного податку | `reestr_edpod`, `kilk_edpod` |
| Платники ПДВ | `pdv` |
| Акцизний податок (пальне, спирт) | `reestr_searpse` |
| Особи, які здійснюють операції з товарами | `reestr_operac_z_tov` |
| Неприбуткові установи | `reestr_nuo` |
| ЦСО | `rro_cso` |

The documentation's example is literally `wget` against the VAT export.

### Mode 2 — REST search, token required

`POST` with a JSON body carrying the query plus a `token`:

| Register | Path | Query fields |
| --- | --- | --- |
| Платники ПДВ | `pdv_act/list` | `kodPdvList`, `tinList` (up to 10), `name` |
| Взяття на облік | `registration` | `tins`, `name` |
| Страхувальники (ЄСВ) | `ev` | `tin`, `name` |
| Акцизний податок | `excise` | `tin`, `name`, `nReg` |
| Операції з товарами | `cli-zed` | `tins`, `name`, `kodPdv` |
| Бюджетна дотація | `obd` | `tins`, `name`, `kodPdv` |
| Неприбуткові | `non-profit` | `tin`, `name` |
| Інформація про РРО | `rro` | `tins`, `name`, `nFis` |
| Книги ОРО | `koro` | `tins`, `name`, `nFis` |
| ПН/РК зі зупиненою реєстрацією | `inv-stopped` | `ipn`, `num`, `crtDate` |
| Екземпляри РРО | `rro-instance` | `sn` |

`registration` returns the shape most useful for counterparty enrichment:
`FULL_NAME`, `TIN_S`, `ADRESS`, `D_REG_STI`, `N_REG_STI`,
`C_STI_MAIN_NAME` (the tax office, with its code), `FACE_MODE` (payer
type) and `C_STAN` (payer state).

`pdv_act/list` returns registration and cancellation dates plus the reason
and grounds for cancellation — enough to say not just "is a VAT payer" but
"was, until this date, for this reason".

## The constraint that decides the design

> The authorisation token is generated by the user themselves, in the
> **private** part of the cabinet, under Налаштування → «Токени відкритої
> частини». A token used in **more than 1000 requests in one day is
> automatically revoked**, and a new one must be generated.

Two consequences, and they point in opposite directions:

1. **The token is a person's, not a service's.** It is minted inside a
   taxpayer's own authenticated cabinet. There is no service credential.
   So a per-tenant lookup either asks every client to paste a token, or
   runs on one token belonging to us — which is 1000 requests a day across
   all tenants, and a revocation that takes out every tenant at once.
2. **The CSV exports need no token.** Mirroring `pdv` and `reestr_edpod`
   on a schedule gives unlimited local lookups with no per-request quota
   and no shared failure mode.

**So the shape is: mirror the bulk exports, use the REST search only for
the rare live check.** That inverts the naive design, and it is the kind of
thing that would have been discovered late and painfully.

Unverified: whether the CSV exports really are unauthenticated in practice,
their size, and how often they are refreshed. That is the first thing to
test, and it is testable without any credential.

## Payment requisites — the question changed

This card originally assumed we would need a directory of budget accounts
keyed by locality, because Taxer generates payment documents with a
different recipient and IBAN per tax and per region.

`reporting-api.md` found a better source: the **private**-part API returns
the taxpayer's own settlement state with `budgetAccountIban`,
`budgetPayerName`, `budgetMfo` and `budgetBankName` per payment type,
resolved for that specific payer.

So the likely answer is **not a directory at all** — it is a per-payer read
against the authority, authenticated by the client's own signature. That
removes the staleness class of bug entirely, since we would read current
requisites rather than mirror a dataset that drifts.

Still to verify, and both are cheap with the owner's key:

- does a payment type with **no assessment history yet** still resolve to
  an account? A newly registered ФОП has nothing on the card.
- does it cover all three payments we need — єдиний податок, військовий
  збір, ЄСВ — or only those with movements?

If either answer is no, the directory returns as a fallback and this
section gets rewritten.

## Near-term value, unchanged

`packages/modules/customers` owns counterparties. `registration` and
`pdv_act/list` would enrich them today, independently of any tax feature.
The blocker is not capability, it is the token model above.

## Open questions

1. Are the CSV exports genuinely unauthenticated, how large are they, and
   how often do they refresh? **Testable now, with no credential.**
2. What are the terms of use for mirroring and re-serving register data
   inside our product?
3. Is there a REST search for the **єдиний податок** register, or only the
   CSV export? The menu lists the register; the documented endpoints do not
   include it.
4. Does one taxpayer's token permit lookups about *other* taxpayers at
   scale, or is that outside its intended use? The 1000/day cap suggests
   the answer matters.
5. The two settlement-state questions above, for payment requisites.
