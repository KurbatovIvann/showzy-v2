# ADR-0014: Drizzle schema lives in packages/db, one file per owning module

- **Status**: Accepted
- **Date**: 2026-08-17
- **Deciders**: owner (+ Claude Fable 5, foundation review)

## Context

Two accepted documents contradicted each other:

- ADR-0005 and blueprint §5 make `packages/db` the schema source and the
  single place migrations are generated from;
- `.cursor/rules/conventions.mdc` required
  `packages/modules/<name>/schema.ts`.

Cross-module foreign keys are pervasive (order items → products, personal
prices → customers, everything → companies). In Drizzle, an FK requires
importing the referenced table object. If schemas lived inside modules,
`orders/schema.ts` would import `catalog/schema.ts` internals — violating the
"modules export only actions and events" boundary, and inviting import
cycles. drizzle-kit also needs one aggregation point regardless.

## Decision

All Drizzle table definitions live in `packages/db/src/schema/<module>.ts` —
one file per owning module, plus `foundation.ts` for core protocol tables and
generated `auth.ts` for better-auth tables. Ownership stays logical, enforced
by three mechanisms:

1. a module's code may import **only its own** schema file
   (`@showzy/db/schema/orders` from `packages/modules/orders`) — ESLint
   boundary rule;
2. a PR from a module task may modify **only that module's** schema file
   (+ generated migrations) — review checklist + CODEOWNERS;
3. declared read-model exceptions (see ADR-0015) are the only way another
   module touches foreign tables.

Migrations are generated by drizzle-kit inside `packages/db` from the
aggregated schema and are ordinary reviewed PRs.

## Alternatives considered

- **`schema.ts` inside each module** (previous conventions.mdc) — rejected:
  cross-module FKs force schema-level imports of other modules' internals,
  weakening the boundary rule exactly where agents copy patterns from; also
  risks import cycles and still needs a central aggregator for drizzle-kit.
- **One monolithic `schema.ts`** — rejected: no ownership signal at all;
  merge-conflict magnet under parallel agents.

## Consequences

- `.cursor/rules/conventions.mdc` updated: module structure no longer
  contains `schema.ts`; it references the module's file in `packages/db`.
- For a table-owning module, its schema task precedes dependent actions
  (`/plan` sequencing): a PR touching
  `packages/db/src/schema/<module>.ts` + generated migration + schema tests.
  Module tasks still never touch `packages/core`.
- `packages/db` becomes append-mostly and heavily reviewed; CODEOWNERS maps
  each schema file to its module.
- Foundation tables (`foundation.ts`) are owned by phase-0/scaffold work and
  are off-limits to module tasks, same as `packages/core`.
